# MigrationBench Asset Registry — 2026-10-25

This directory is a **provenance-aware, additive inventory** of MigrationBench models, data assets, evaluations, failures, and open audit items. It was initialized from the three supplied Obsidian documents plus the linked current campaign locations. It is deliberately conservative: a campaign label is not promoted to a checkpoint identity unless its lineage is known, and scheduler completion is not promoted to scientific acceptance.

## Key design rule

The fact grain is **model identity × task/operator × material/system × campaign**. `coverage` is therefore the central matrix. It uses nullable `model_id` only for an explicitly aggregate campaign record whose source did not safely reveal the per-model mapping; those rows carry a gap that explains why.

## Model taxonomy

1. Foundation: MACE-MP, MACE-OMAT-0, MACE-MH, and MatPES PBE OMAT fine-tuned.
2. Train from Scratch: current Lmax1 Scratch-600K and Scratch-MultiT, each with seeds 123/234/345; historical/5%/Lmax2 variants remain separate.
3. Fine-tuning: Fine-tuning-600K and Fine-tuning-MultiT, each with seeds 123/234/345; grouped A2 and legacy variants remain lineage-pending.
4. Campaign-only labels are stored as `CAMPAIGN_LABEL`, never silently merged with canonical checkpoint IDs.

## Scientific boundaries encoded in the registry

- Fixed-path NEB and endpoint-only self-relaxed NEB are distinct task records and must not be pooled into a barrier ranking.
- Cr61 and Cr81 NEB are distinct systems.
- Interlayer DFT reference rows retain `COMPLETED_BUT_SCF_WARNING`; fixed-path results are diagnostics, while self-relaxed paths are endpoint-only MLIP proxies.
- Failed/unstable MD, optimizer nonconvergence, provenance gaps, and excluded legacy artifacts remain queryable rather than being deleted.

## Revision 1 manuscript claim lineage (additive schema proposal)

The existing Revision 1 tables provide a useful 52-object figure/table registry and a 639-row extraction
inventory, but they do not by themselves close the semantic chain from a sentence or numeric cell to a
specific result row, run/attempt, exact checkpoint, input/output artifact, and figure/table export. The
separate audit of the 338 main/SI prose segments classified 0 as `TRACEABLE`, 32 as `PARTIAL`, and 306 as
`MISSING` under its exact-key matcher. These are navigation/provenance statuses, not scientific truth scores.

Migration 004 adds stable IDs and typed foreign keys for:

- immutable manuscript source blobs and exact-text claims with 1-based line spans;
- nested figure/table/panel/cell/caption objects, optionally linked to the existing
  `rev1_results_index(item_id, panel)` composite key;
- derived result rows/cells, runs and attempts, exact model-checkpoint SHA-256, protocol keys,
  process/script/environment identities, and hash-addressed artifacts;
- typed links (`claim_object_links`, `claim_result_links`, `object_result_links`, `result_run_links`,
  `result_artifact_links`, `run_artifact_links`, `run_process_links`);
- explicit caption/release/export issues, diagnostic repeatability evidence, and active-learning decisions
  with a baseline, follow-up run, outcome result, named evaluation protocol/gate, and an
  `NOT_EVALUATED` default gain status.

Evidence status (`TRACEABLE`, `PARTIAL`, `NOT_LINKED`, `NOT_RUN`, `MISSING`, `HOLD`, `CONFLICT`) is kept
separate from scientific status (`PROVENANCE_PARTIAL`, `PROVISIONAL`, `SUPPORTED`, `REJECTED`,
`NOT_ASSESSED`, `EXCLUDED`). Exact SHA-256, not model labels, seeds, or nearby paths, is the identity key
for a checkpoint join. `CAPTION_MISMATCH`, source-release mismatch, and missing manual export remain visible
issues. No `TRACEABLE` state is created by applying the migration; each relation still needs source evidence
and review.

### Safe schema preview

The committed `migrationbench_asset_registry.sqlite` and its CSV mirrors remain unchanged. On a temporary
copy of a registry that already has migrations 001–003 applied, use:

```bash
cp migrationbench_asset_registry.sqlite /tmp/migrationbench_claim_lineage_preview.sqlite
sqlite3 /tmp/migrationbench_claim_lineage_preview.sqlite \
  < migrations/004_revision1_claim_lineage_graph.sql
sqlite3 /tmp/migrationbench_claim_lineage_preview.sqlite \
  < manuscript_lineage_queries.sql
```

The second command will run the read-only examples against empty new tables and therefore return no claims
or lineage records. This is intentional. Do not rebuild the source DB, alter the submitted paper, or import
rule-extracted claim rows as reviewed scientific claims as part of this schema change. Populate the graph only
from item-level, hash-identified evidence with retained failed, held, provisional, and not-run states.

## Updating safely

1. Add immutable checkpoint details (`artifact_path`, SHA256, base checkpoint, training seed) before merging aliases.
2. Add one `coverage` row per model × task × system × campaign, preserving `run_status` and `scientific_status` separately.
3. Add a source and asset locator for every new data package.
4. Close a `gaps` row only with a linked audited source. Do not overwrite raw or historical rows.
